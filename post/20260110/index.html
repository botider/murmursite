深入淺出 Copilot Subagent：擺脫 Context 泥沼

January 10, 2026

在這篇文章中，我想探討以下幾個問題：

  • 為什麼我們需要 Subagent？
  • 在真實的開發流程中如何應用？
  • 它與 Skill 有什麼本質上的區別？

為什麼需要 Subagent？

在 2025 年 10 月，GitHub Copilot for VS Code 將 “chatmodes” 升級為 “agents”，並帶來了強大的 “subagent” 能力。這讓主 Agent 能夠啟動「另一個擁有乾淨 Context、甚至使用不同模型的獨立 Agent」。

單一 Agent 最大的痛點在於：當對話時間拉長，Context 累積過多雜訊後，回應品質會顯著下降（變笨）。

Subagent 的出現解決了這個問題：

  1. 乾淨的上下文 (Clean Context)：每次任務都從零開始，避免歷史包袱。
  2. 非阻塞執行 (Non-blocking)：多工處理時，Subagent 在背景平行運作，不會卡住你的主對話框。
  3. 計畫委派 (Delegation)：在 Plan Mode 下，主 Agent 可以將拆解後的步驟交由 Subagent 執行。

實際應用 (Real Dev Scenario)

1. 設定 (Setup)

首先，我們需要在 .github/agents/ 目錄下定義 Agent：

  • Scope：設定是個人專用還是專案共享。
  • Description：這是關鍵。你需要清楚描述這個 Agent 能做什麼 以及 何時該用。（例如：當你需要修改 C# 程式碼時… 請使用此 Agent）。
  • Tools：定義這個 Subagent 可調用的指令、MCP 或 Skill。

2. 執行 (Run)

啟動方式相當靈活：

  • 明確執行：透過 $runSubagent 指令手動觸發。
  • 隱式執行：讓主 Agent 根據對話內容，智慧判斷是否呼叫 Subagent。
  • 平行處理：

    “Research the authentication, database, and API modules in parallel using separate subagents” (使用不同的 Subagents 同時研究驗證、資料庫和 API 模組)

  • 串接協作：

    “Use the code-reviewer subagent to find performance issues, then use the optimizer subagent to fix them” (先用代碼審查 Agent 找出問題，再用優化 Agent 進行修復)

3. 工程風險 (The Risk in Engineering)

遷移成本 (Migration) 如果多個 Subagent 依賴相同的專案業務邏輯，一旦業務邏輯變更，我們就必須 Copy/Paste 到每個 Agent Profile 中進行修正。這種重複性維護違反了 DRY 原則，是未來需要解決的挑戰。

與 Skills 的比較

很多人會混淆 Subagent 和 Skill。簡單來說：

  • Skill：利用「漸進式揭露 (Progressive Disclosure)」來縮減 Context。它的核心在於將常用的指令抽象化，封裝成工具。
  • Subagent：則是提供一個全新的執行環境與思考模型。
