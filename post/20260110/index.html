深入淺出 Copilot Subagent：擺脫 Context 泥沼與微服務化的既視感

January 10, 2026

談談 GitHub Copilot Subagent。

這其實已經是 2025 年底的事了，應該不少人都已經在用了，但我還是稍微前情提要一下。 在 2025 年 10 月左右，GitHub Copilot for VS Code把原本的 “chatmodes” 升級成了 “agents”，並且開放了所謂的 “subagent” 能力。這功能簡單來說，就是讓你的主 Agent 可以再叫出另一個獨立的 Agent 來幫忙做事，而且這個新的 Agent 擁有乾淨的 Context，甚至可以使用不同的模型。

乍聽之下好像很厲害，但也讓人覺得有點困惑：我們原本不是追求一個「全知全能」的 AI 助手嗎？怎麼現在反而要把他拆成好幾個小助手？這走回頭路的感覺，看起來是件滿弔詭的事情。

但這並不是什麼新鮮事，在軟體架構的發展史上其實就這樣了，甚至對有些架構師來說這劇本眼熟到不行。 要解釋這個說法，我們要從頭開始看，先回答：「為什麼我們需要 Subagent」

這一切的問題核心，都在於那個老掉牙的「Context 泥沼」。 不管 LLM 的 Context Window 從 32k 變成 128k 甚至 12800k，單一 Agent 最大的痛點始終沒變：當對話時間拉長，Context 累積過多雜訊後，回應品質會顯著下降（變笨）。這就像是你把整本 Wiki 丟給他，然後問他這頁第三行的錯字在哪，他反而會迷失在資訊海裡。

Subagent 的出現基本上就是為了解決這個問題，它的核心價值有三點：

  1. 乾淨的上下文 (Clean Context)：每次任務都從零開始，沒有前面的對話包袱。
  2. 非阻塞執行 (Non-blocking)：就像是非同步函式 (Async)，Subagent 在背景跑，你可以繼續跟主 Agent 聊天。
  3. 計畫委派 (Delegation)：主 Agent 變成專案經理，負責拆票，Subagent 負責解票。

知道「為什麼」之後，我們來看看「怎麼做」。 在技術實作上，我們需要在 .github/agents/ 目錄下定義 Agent。你需要設定 Scope（誰能用）、Description（這隻 Agent 能做什麼）、以及 Tools（他能用什麼工具）。 這是不是聽起來很耳熟？ 這不就是微服務 (Microservices) 的服務定義檔嗎？

把這個技術放到軟體工程的脈絡來看，你會發現這整件事跟微服務的興起如出一徹。 以前我們寫 Monolith，所有邏輯都在一起，Context 很大很雜（Global variable 滿天飛）。後來我們受不了了，把它拆成 Microservices，每個 Service 專心做一件事，資料庫切開，Context 乾淨了。

現在 AI 也是一樣。 原本的主 Agent 就是那個 Monolith，它什麼都知道，但也什麼都混在一起。Subagent 就是拆出來的 Microservice，專門負責「Code Review」、專門負責「寫 SQL」、專門負責「寫文件」。

這樣的好處顯而易見：你可以平行處理。 你可以跟主 Agent 說：“Research the authentication, database, and API modules in parallel using separate subagents”（請用不同的 Subagents 同時研究驗證、資料庫和 API 模組）。 若是以前，他得一個一個查，吐出一大串你看不完的文字；現在他派了三個小弟去背景跑，最後再回來回報。

但是，凡事都有代價。

微服務最為人詬病的缺點，在 Subagent 架構下也完全繼承了。還記不記得微服務最大的痛？Code Duplication 與維護成本。

如果我有多個 Subagent 都需要知道公司的「業務邏輯」（例如：訂單狀態機怎麼轉），我就得在每個 Agent 的 Prompt 或 Knowledge Base 裡都寫一遍。 一旦業務邏輯變了，我就得打開 .github/agents/ 下面的每一個檔案去改。這樣違反 DRY (Don’t Repeat Yourself) 原則的重複性維護。 小專案可能業務邏輯變動性不高，但是如果考慮到長期維護的專案，如果只單純設定好Subagent，就期望可以盲目使用AI產出是不可能的。

另外最近Anthropic在2025/12發佈了Agent Skills標準 很多人會搞混，覺得 Skill不也是可以縮減Context嗎？

簡單的二分法是：

  • Skill 是「工人的技能」，它是利用「漸進式揭露 (Progressive Disclosure)」來讓 AI 在需要執行到某個Skill描述(Skill Description)有關連任務的時候，才去讀取更多的Skill Context，也因此沒有使用到的Skill，就不會消耗大量的Context，只會消耗Skill Description。

  • Subagent 是「工人 (Workers/Services)」，它是提供一個全新的執行環境與思考模型，目的是隔離 Context。 一個是給原本的工人一把新錘子（Skill），一個是直接請一個新的工人帶把錘子進場（Subagent）。

那 Subagent　的實際開發應用情境？ 有的。舉例當我在處理大型 Refactor 的時候，我就會叫一個 Subagent 專門去爬 Dependency Graph，另一個 Subagent 專門幫我寫單元測試。 這種「分而治之 (Divide and Conquer)」的策略，在人類管理專案時有效，在 AI 管理 Context 時也同樣有效。

從軟體工程角度來看Subagent．我的感覺是，這個技術的本質跟以前一些概念很像，它一直在發生。從 Monolith 到 Microservices，再從 Chat 到 Agents，我們始終在做同一件事：管理複雜度。 Subagent 雖然解決了 Context 變髒的問題，但也引入了架構維護的成本。

所以應該解決的問題還是一樣的，那就是如何在「靈活性」與「維護性」之間取得平衡。這件事會跟 AI 有關，我覺得也只是因為剛好我們現在手上的工具變成了 LLM，但背後的工程思維，其實一點都沒變。
