深入淺出 Copilot Subagent：擺脫 Context 泥沼與微服務化的既視感

談談 GitHub Copilot Subagent。

這其實已經是 2025 年底的事了，應該不少人都已經在用了，但我還是稍微前情提要一下。 在 2025 年 10 月左右，GitHub Copilot for VS Code把原本的 “chatmodes” 升級成了 “agents”，並且開放了所謂的 “subagent” 能力。這功能簡單來說，就是讓你的主 Agent 可以再叫出另一個獨立的 Agent 來幫忙做事，而且這個新的 Agent 擁有乾淨的 Context，甚至可以使用不同的模型。

乍聽之下好像很厲害，但也讓人覺得有點困惑：我們原本不是追求一個「全知全能」的 AI 助手嗎？怎麼現在反而要把他拆成好幾個小助手？這走回頭路的感覺，看起來是件滿弔詭的事情。

但這並不是什麼新鮮事，在軟體架構的發展史上其實就這樣了，甚至對有些架構師來說這劇本眼熟到不行。 要解釋這個說法，我們要從頭開始看，先回答：「為什麼我們需要 Subagent」

這一切的問題核心，都在於那個老掉牙的「Context 泥沼」。 不管 LLM 的 Context Window 從 32k 變成 128k 甚至 12800k，單一 Agent 最大的痛點始終沒變：當對話時間拉長，Context 累積過多雜訊後，回應品質會顯著下降（變笨）。這就像是你把整本 Wiki 丟給他，然後問他這頁第三行的錯字在哪，他反而會迷失在資訊海裡。

Subagent 的出現基本上就是為了解決這個問題，它的核心價值有三點：

  1. 乾淨的上下文 (Clean Context)：每次任務都從零開始，沒有前面的對話包袱。
  2. 非阻塞執行 (Non-blocking)：就像是非同步函式 (Async)，Subagent 在背景跑，你可以繼續跟主 Agent 聊天。
  3. 計畫委派 (Delegation)：主 Agent 變成專案經理，負責拆票，Subagent 負責解票。

知道「為什麼」之後，我們來看看「怎麼做」。 在技術實作上，我們需要在 .github/agents/ 目錄下定義 Agent。你需要設定 Scope（誰能用）、Description（這隻 Agent 能做什麼）、以及 Tools（他能用什麼工具）。 這是不是聽起來很耳熟？ 這不就是微服務 (Microservices) 的服務定義檔嗎？
