為什麼玩家會討厭AI開發的遊戲?

Larian Studios 宣稱使用AI開發遊戲，然後就被炎上了

前陣子從Manny大大臉書看到Larian Studios因為宣稱在開發新作「神諭」時，有使用AI來做創意發想，結果被玩家炎上

Manny Facebook 傳送門

然後Larian創辦人承諾他們會開個AMA (Ask Me Anything)，讓玩家更了解他們的想法

現在AMA剛結束不久，我想針對AMA裡面玩家提到AI相關的問題做個整理 一方面是想了解玩家對AI的看法 另一方面也是想了解遊戲開發者如何在AI與玩家之間的矛盾找出生存之道

誰是Larian Studios？很重要嗎？

簡單科普一下，他們是一家比利時遊戲開發公司，創作了許多知名遊戲作品，像是《神諭：原罪》和2023年榮獲多項大獎的《柏德之門 3》，以我這位不太玩回合制戰鬥的輕度玩家，「神諭:原罪2」也讓我享受了近40小時美好的遊戲沉浸時光

他們的遊戲怎麼讓玩家感受到沉浸感?

即使已經快5年沒玩了，我依然還記得戰鬥中的技能與環境互動產生的效果： 使用水元素+火元素產生蒸氣，干擾敵人視線的玩法，還有善用地形推人下懸崖 等到我拿到傳送手套以後，將各種環境道具傳送到敵人頭上，或是把敵人傳送丟下懸崖等等成了我的樂趣

然後遊戲中也提供幾個可累積好感度的腳色，種族從精靈到亡靈蜥蜴人都有，好感度高可解鎖親密互動，要表現出跨種族的戀愛真的很佩服開發者的腦袋

另外Larian Studio在遊戲的語音配音也投入大量資源 從遊戲開發者的角度來看，開發一個劇情自由度高，文本量大，又要劇情語音配音簡直是作死，但他們依然盡可能將主要腳色和關鍵劇情補上語音

就是這種驚人規格的遊戲，讓很多玩家覺得就像蒐集手工藝術品一樣，成為他們的作品的忠實粉絲

…

…

…

… 直到製作人說他們在創意發想流程使用AI，粉絲崩潰

為什麼玩家反對 AI？

世界上的任何事物，有些人喜歡，有些人不喜歡，這都很常見 為何遊戲開發商使用AI，會嚴重到要開AMA來親自跟玩家對談？

為了回答這個問題，我整理了來自 Reddit AMA 討論串中的部分玩家論點與問題：

  • AI 只是一個工具，耗費大量能源，而且在未經藝術家許可的情況下複製藝術作品。
  • AI 產品沒有靈魂；我只想玩人類用心製作的遊戲。
  • AI 提升了公司產品開發效率，但也導致部分用心的遊戲開發者失業。
  • Larian的每位藝術家或員工都願意使用 AI 嗎？還是被迫為了工作效率而使用？
  • 在概念階段，過去是人類腦力激盪，而概念會影響遊戲的核心。當概念發想工作開始使用 AI 時，遊戲核心就只剩下AI。
  • Larian 使用 AI 的詳細工作流程是什麼？
  • Larian 如何確保 AI 在概念發想階段生產出來暫時性的素材，會在最終產品中被妥善處理？

我好好奇 Larian 究竟是站在玩家還是站在AI

但在將Larian的回應整理出來之前

我也查了遊戲產業鏈中另一個重要的腳色:遊戲平台對於AI的政策

我想嘗試釐清我無法回答的問題:

  • 平台是使用者創作內容的平台，那AI的創作算是使用者創作嗎?
  • AI算是一種程序化生成嗎？如果是，那為何直到現在才看到玩家強烈對AI生成的遊戲表達不滿？

遊戲平台的政策

Steam遊戲平台在2024/1/10發布了「AI Content on Steam」的公告 遊戲開發者除了要主動聲明遊戲有使用到AI (無論是預先生成素材或是及時生成)，還需要承諾遊戲不包含違法或侵權的內容 也就是說，平台採取開放但是嚴格監管的方式，在AI與玩家之間取得平衡

深入淺出 Copilot Subagent：擺脫 Context 泥沼與微服務化的既視感

談談 GitHub Copilot Subagent。

這其實已經是 2025 年底的事了，應該不少人都已經在用了，但我還是稍微前情提要一下。 在 2025 年 10 月左右，GitHub Copilot for VS Code把原本的 “chatmodes” 升級成了 “agents”，並且開放了所謂的 “subagent” 能力。這功能簡單來說，就是讓你的主 Agent 可以再叫出另一個獨立的 Agent 來幫忙做事，而且這個新的 Agent 擁有乾淨的 Context，甚至可以使用不同的模型。

乍聽之下好像很厲害，但也讓人覺得有點困惑：我們原本不是追求一個「全知全能」的 AI 助手嗎？怎麼現在反而要把他拆成好幾個小助手？這走回頭路的感覺，看起來是件滿弔詭的事情。

但這並不是什麼新鮮事，在軟體架構的發展史上其實就這樣了，甚至對有些架構師來說這劇本眼熟到不行。 要解釋這個說法，我們要從頭開始看，先回答：「為什麼我們需要 Subagent」

這一切的問題核心，都在於那個老掉牙的「Context 泥沼」。 不管 LLM 的 Context Window 從 32k 變成 128k 甚至 12800k，單一 Agent 最大的痛點始終沒變：當對話時間拉長，Context 累積過多雜訊後，回應品質會顯著下降（變笨）。這就像是你把整本 Wiki 丟給他，然後問他這頁第三行的錯字在哪，他反而會迷失在資訊海裡。

Subagent 的出現基本上就是為了解決這個問題，它的核心價值有三點：

  1. 乾淨的上下文 (Clean Context)：每次任務都從零開始，沒有前面的對話包袱。
  2. 非阻塞執行 (Non-blocking)：就像是非同步函式 (Async)，Subagent 在背景跑，你可以繼續跟主 Agent 聊天。
  3. 計畫委派 (Delegation)：主 Agent 變成專案經理，負責拆票，Subagent 負責解票。

知道「為什麼」之後，我們來看看「怎麼做」。 在技術實作上，我們需要在 .github/agents/ 目錄下定義 Agent。你需要設定 Scope（誰能用）、Description（這隻 Agent 能做什麼）、以及 Tools（他能用什麼工具）。 這是不是聽起來很耳熟？ 這不就是微服務 (Microservices) 的服務定義檔嗎？
