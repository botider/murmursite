你有在使用Claude Code嗎？那你有沒有聽過Github Copilot？

這些 AI coding agent 都一樣嗎？有什麼本質差異？這篇文章用最簡單的比喻，幫助你快速理解「AI 編程助手」的核心概念、產品定位，以及各家特色。

這篇文章適合

傳統的寫程式體驗 be like…

在沒有 Claude Code 這類 agent 產品時，單純用 ChatGPT 寫程式是什麼體驗？

在 Claude Code、Copilot 等「AI coding agent」出現前，許多開發者會用 ChatGPT（或一般 LLM 聊天介面）協助寫程式。這種流程大致如下：

  • 遇到需求或 bug，把問題描述貼到 ChatGPT，請它產生程式碼
  • 手動複製貼上到本地 IDE，自己整合到專案
  • 如果ChatGPT的回答不符合期待，要自己再補充細節、反覆跟ChatGPT溝通
  • ChatGPT 不會主動讀取你的專案結構、檔案內容，無法自動追蹤 import 或跨檔案邏輯
  • 測試、debug 仍需自己執行，AI 不會自動驗證結果

這種「AI 聊天輔助」模式，雖然能加速查詢與產生範例，但：

  • 需要大量人工來回溝通、搬運程式碼
  • AI 無法真正理解你的專案全貌
  • 缺乏自動化的 context 管理與工具整合

而像 Claude Code 這類 Agent Coding 產品，則能直接存取專案檔案、主動搜索問題的資料、甚至自動執行測試與修正，大幅減少人工搬運與溝通成本，讓 AI 真正成為「主動型協作者」。

如何升級寫程式的體驗

很簡單

如果你已經會用VSCode寫程式，VSCode其實都支援Copilot和Claude Code

兩個產品都可以透過VSCode Extension安裝，但是Claude Code還要額外安裝他的CLI，所以入門門檻稍微高了一點 新手我覺得使用Copilot體驗會簡單一點

這篇文章重點是講Agent Coding Tool的觀念，所以安裝工具的細節就不贅述

你只需要知道，安裝了Copilot以後，VSCode裡面會Copilot對話框 (就像最廣為人知的ChatGPT的介面) 你只要下命令給Copilot就好

例如

「請用Python幫我寫一個Hello World」

Copilot會自己編輯檔案，你再也不需要複製貼上了

除了不需要複製貼上，Agent Coding Tool還有沒有其他好處

無論是 Claude Code、Copilot 或其他先進 AI coding agent，本質上都遵循一個「Agentic loop」：

  1. 收集脈絡（Gather Context）：
    • 讀取你的需求、專案檔案、錯誤訊息、測試結果等，理解目前狀況。
  2. 採取行動（Take Action）：
    • 根據理解，選擇適合的工具（如搜尋、編輯檔案、執行指令、查文件），逐步執行任務。
  3. 驗證結果（Verify Results）：
    • 檢查行動後的結果（如測試是否通過、錯誤是否消失），必要時重複調整，直到達成目標。

這三個階段會不斷循環，AI 會根據每次獲得的新資訊自我修正，直到任務完成。你可以隨時介入、補充脈絡或調整方向。

這就是所謂的「Agentic loop」——AI 不只是單次回答，而是像一位能主動規劃、執行、驗證的協作夥伴。

Claude Code 和 Copilot 用起來的體驗會有差異嗎

當然會，不然他們怎麼賺錢？

在描繪體驗之前，我覺得把Agent工作流程具象化，會更容易吸收接下來的觀念 這裡先分享一個令我印象深刻的開源專案：

  • vibecraft 專案

這個專案將Agent工作的流程視覺化，也就是說裝了這個套件，當AI在工作時，你可以看到3D小人真的在工作桌前面工作

腦袋中有了具體的Agent工作畫面後，來談談Agent Coding Tool的差異：

打個比方，Claude Code 和 Copilot就像是兩間工廠

兩間工廠都是依據你輸入的文字訊息，依照他們工廠內部的設定最終生產出讓你滿意的結果

但是兩間工廠內的管理方式不同

舉例來說Claude Code的工廠內部工作指南可能會是：

在交付結果之前，先自我審查是否符合要求，並自行修正錯誤

而Copilot的工作指南可能是：

給予最符合使用者意圖的結果

而這個「內部工作指南」，其實就是 System Prompt，也就是 Agent 內部的一段文字，引導工匠(LLM Model)的思考方式最後產生結果

所以一個簡化的工廠工作流程是：

使用者輸入請求(user input) -> 工廠附加內部工作指南 (system prompt + user input) -> 工匠產生結果 (LLM Model)

即使你在Claude Code 和 Copilot都選用同一個工匠(例如都選擇了Claude Opus 4.5模型)，結果還是會不同，體驗也不同

只要會打字，就會使用Agent Coding Tool嗎

遠遠不是

多用幾次，你可能會發現實際的工作流程可能是：

想要寫新的Code -> 輸入文字請Agent做完 -> Agent做出不理想的東西 -> 發現還要給他更多指示 -> 思考如何給予正確的指示 -> 重新試試看你的新指令 -> Agent又做錯了 -> ...

這是Agent Coding Tool的問題嗎？ 是的

這可以修正嗎？當然

想像你花錢買了這間工廠的產能，但是工廠其實可以針對你的需求進行客製化， 而這個客製化程度，可以是只有在你目前做的專案，也可以是跨專案，針對你個人打造的設定

除了打字之外，還能怎麼使用Coding Tool

前面提到，既有的工作流程可能會遇到Agent產出的結果不符合你的期待

還記得我們之前提到工廠內部有「工作指南」嗎？ 其實你也可以自己設定自己想要的工作指南 當客製化你自己的工作指南，會讓Agent更懂你的需求

舉例來說，我現在的Coding專案是Python語言，我可以在工作指南內放入Python的Linter Rule

我也可以寫份指南，要求Agent遵守TDD(Test Driven Design)的開發原則

這份工作指南的內容，在Claude Code和在Copilot是通用的

(只是兩間工廠有各自的特殊規定，工作指南要放在各自規定的資料夾下，並且符合特定命名格式才能正確運作)

這個客製化工作指南，在Claude Code的關鍵字是CLAUDE.md，在Copilot則是instruction.md

繼續升級：了解 MCP (Model Context Protocal)

繼續講講其他客製化的方法

舉例來說，當你被交付一項工作，例如要實作一個UI 通常你拿到的就是一個Figma網址，裡面有設計師做好的UI元件

傳統工作流程是人工去檢視Figma的元件尺寸規格，手動寫代碼 因為這些Figma元件規格是很難透過自然語言去描述

其實你可以讓Agent自動處理Figma的事情

透過安裝Figma客製化工具，你其實就讓Agent具備了分析Figma的能力

而你需要做的事情就是將Figma文件的網址貼到Agent對話框，並且給予一些指示 Agent就可以開始實作Figma的UI

上面這個客製化工具，稱為 MCP (Model Context Protocal)

這是一種通用的協定，有興趣的可以自行搜尋

聽起來升級很簡單？來談談Context Window

如果你以為升級就是不斷地堆疊「工具」和「工作指南」，這樣是不行的

想像每個工匠(LLM Model)都有自己的工作台

工作台有大小限制

如果你的輸入文字訊息太大，工廠內部指南，以及各種客製化工具太多，工匠只能處理工作台能容納的東西，那些無法放在工作台上的東西則會被丟棄，工匠是不會去處理的

因此你沒辦法一直堆疊工具或工作指南

而這個工作台大小限制，就是Context Window

事實上，除了安裝的客製化工具, 你在跟Agent一來一回的對話過程，對話紀錄也會被視為放在工作台上的物品，換句話說對話紀錄也會佔據Context Window

所以有人說跟Agent聊久了，發現他變笨了回應總是鬼打牆一模一樣，就是工作台已經放不下新東西而導致的

繼續升級：什麼是Skill

要如何解決工作台大小限制的問題呢？

很簡單，只把重要的東西放在工作台，就可以讓工作台變乾淨

這就是Skill的好處

不妨把Skill想像是類似工作指南的東西，但與工作指南不同的是：

Skill只有描述(Description)會放在工作桌，其餘Skill的細部內容，則是工匠認為需要用到這個Skill時，才會將Skill的細部內容放到工作台上

具體來說，Skill 可以應用於：

自動化的邏輯流： 雖然工匠（模型）很聰明，但有時候面對複雜任務（例如：部署到雲端、寫單元測試）會漏掉步驟。Skill 就像是一份已經驗證過的 SOP 檢查表，確保工匠每一步都走在正確的軌道上。

能力的擴充包： 有些 Skill 是工匠本來不會的（或者不擅長的），透過載入特定 Skill，工匠就像瞬間學會處理特定領域任務的技能，因此在工作時產出會更不容易出錯。

具體的例子：

GitHub Skill： 讓工匠知道「如何正確地發 PR、處理衝突」。

Test Skill： 讓工匠知道「寫完 Code 後，必須主動去找測試目錄並運行 npm test」。

還記得 MCP 嗎？雖然都是擴展能力，但 MCP 和 Skill不一樣。 我舉個例子： GitHub MCP：讓工匠有工具將GitHub的資料拿到工作台，例如 Pull Request Description

如果說 MCP 是工匠手邊實體的「工具箱」（例如：扳手、螺絲起子），那麼 Skill 就是工匠腦海中「如何使用這些工具來完成特定複雜任務的知識」

繼續升級：精打細算靠SubAgent

你在使用Copilot時，是否有發現不同的工匠(模型)會有不同的計費方式？

通常比較貴的模型，產出品質都比較穩定，就像比較厲害的工匠，薪水當然比較高

舉例來說，摘要這段內容、或修改標點符號

SubAgent其實不只能當工讀生，也可以是臨時調派來的「專業工匠群」

還記得我們提到的工作台(Context Window)限制嗎？ 當遇到超大型任務時，一個工匠的工作桌可能會無法消化這個任務，導致產出結果品質不良

SubAgent的特性是，每個工匠都會分配到各自獨立的工作台

利用這個獨立工作台的特性，我們可以思考如何將大型複雜的工作拆分成不同領域的工作，並交給我們認為合適的工匠(LLM Model)，依照不同專業技能(Skill)使用不同的工具(MCP)處理工作

這裡有個指令範例提供參考，讓你一窺如何分派大型任務：

「這是一個大型重構任務，我需要將專案中的所有 API 從 REST 改為 GraphQL。請你：

先分析影響範圍，並列出需要執行的子任務清單。

啟動 Subagents（或子程序） 並行處理不同目錄下的檔案轉換。

每個子任務完成後需獨立運行測試。

最後由你匯總並回報進度。」

結語

來複習一下上面說的觀念

  • Agent Coding Tool：工廠本身，決定工作環境與流程，例如Claude Code / Copilot
  • 模型 (LLM Model)：工廠裡的工匠，負責實際工作（但偶爾會出錯），例如Claude Opus 4.5
  • 工廠內部工作指南 (System prompt)：工廠給工匠的「內部指令」
  • 工作台 (Context window)：工匠的工作台，有大小限制
  • 工具 (MCP)：工匠可用的工具箱，例如 Figma MCP
  • 技能 (Skill)： 工匠大腦裡的「標準作業程序 (SOP)」或「專業證照」
  • SubAgent： 工讀生，也可以是一群專業工匠，特性是各自擁有獨立的工作台
